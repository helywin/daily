## 1. 定位置信度进入 A*：最短路线不一定是无人机真正能够完成的路线

**时间回补：v1 2026-10-29 16:51 UTC。** [Optimal Path Planning with Localization constraints](https://arxiv.org/abs/2610.40429)。

### 为什么重要

GPS 不可用时，无人机的惯导或视觉里程计误差会随运动累积。地图上看起来最短的通道可能很久都没有可用于重新定位的外部观测；绕行接近蜂窝基站或已知地标反而能保持全程位置可信。传统 A* 只评价距离或时间，通常不会把状态估计的协方差当成硬性约束。

本研究把 EKF 的预测与更新嵌入 A* 搜索，搜索节点同时携带位置估计和协方差。算法仅保留能够满足预先设置的定位不确定性上界的路径，同时保持所使用启发函数的可采纳性和一致性，从而讨论**可行路径集合内**的最优性，而非对任意轨迹的全局物理最优性。

### 算法模块与数学边界

~~~text
地图 + 起点/终点 + 定位地标位置
               ↓
        A* 候选拓展
               ↓
     运动模型传播 EKF 协方差
               ↓
   经过地标时更新观测与协方差
               ↓
   协方差违反上限？——是→剪枝
               ↓ 否
    累计行程代价 + 启发式估价
               ↓
       定位风险受约束的路线
~~~

工程中不能把协方差简单映射成一个固定附加距离惩罚：在风险不可接受时，再短也不应执行。还须明确是约束位置协方差迹、最大特征值，还是单独某个方向的方差；不同定义会给出不同的可行集合。

### 传感器、动力学假设与风险

依赖正确的运动噪声、EKF 线性化、地标位置、观测噪声与更新可见性。蜂窝塔“附近可定位”只是论文模型中的地标假设，真实通信基站不会无条件提供高精度三维位姿观测。错误的数据关联与失效地标也会让协方差虚假收缩。

论文在 Monte Carlo 和 PyBullet 四旋翼模拟中与 RRT*、PRM 对比，报告更短且满足不确定性限制的可行路线；摘要未提供统一的真实飞行误差或可跨硬件复用的规划延迟。

### 可复现性、适合谁与工程落地启发

尚未核实完整官方一键运行代码。最小复现可在二维占据地图上实现 A* + EKF，设置一条短但长期无观测的走廊，以及一条略长却有地标的路线，比较普通 A*、距离加权风险 A*、协方差硬约束 A*。记录路径长度、实际定位误差、超限次数、搜索节点数与 P95 求解耗时。

适合 **GNSS 拒止无人机、地下通道机器人、视觉/LiDAR 退化时的全局路径选择**。对于已有 FAST-LIO/ESKF 的系统，可先把预测不确定性作为高层规划约束，避免直接改动高频状态估计。

## 2. PhysVLMM：空间语义地图开始记住“这扇门怎样被拉开”

**时间回补：v1 2026-10-29 17:35 UTC。** [PhysVLMM 论文](https://arxiv.org/abs/2610.40539)。

### 为什么重要

传统 Vision-Language-Map 可以记录冰箱、抽屉、门把手的位置与语义，却很难回答“我沿这个方向施加这点力，门会打开吗”。仅观察门的外观甚至看它运动一次，不能唯一识别其完整受力动力学。PhysVLMM 为场景图中的每个可动部件维护**相互作用条件下的物理后验**；真正执行拉动之后，才用实测反馈更新该对象，并在相似对象间共享受限制的证据。

### 算法模块

~~~text
视觉/语言/场景图 → 可动部件及候选关节类型
                           ↓
                  交互前动力学先验
                           ↓
             有方向的拉动/力觉反馈
                           ↓
           被拉部件的后验更新
                           ↓
        相似部件之间有条件地共享证据
                           ↓
   查询: 某个动作在给定风险下会成功吗？
                           ↓
             允许 / 拒绝 / Abstain
~~~

特别值得借鉴的是拒绝过度推断：测到一个方向上的拉动响应，不能自动认为其余方向都已经学会；对证据不足的查询允许 **abstain（弃答）**，让规划器先探测而不是凭空补齐参数。

### 实验结果、边界与鲁棒性

作者在 **18 个家庭**的真实门、抽屉上测试。留出拉动中，关节类型判断正确率 **86%**，所比较单视图学习法为 **48%**。拉动响应概率预测误差 CRPS **0.323**，对照可微仿真 **0.544**；单次计算约 **13 ms**，对照仿真约 **230 s**。后验将终点位置误差从 **0.460** 降到 **0.270**。这些指标分属不同任务与评价方式，不代表任意机械臂可以以 13 ms 完成真实关节力控。

论文还检查风险阈值在 0.02–0.30 的“误判安全”控制情况。需要特别核对试验设定、校准样本和家庭分布：离开这类任务以后，风险承诺并不自动成立。

### 可复现性、适合谁与工程落地启发

官方完整工程源码尚未确认。可以选择三扇不同铰链门、两个滑轨抽屉，固定机器人力/位移采样，比较单次观测、无跨对象共享、按相似度共享后验的动作成功预测质量。保留实测拉力、关节行程、后验宽度和弃答率。

适合 **室内语义建图、机器人开门/抽屉操作与基于世界模型的任务规划**。工程上应该将对象的物理可信度与普通几何地图分离；力矩限制及碰撞停止依旧由本地控制器强制执行。

## 3. Teaching a Tree to Recover：让 LLM 只教会 MPC 恢复规则，而不是每次卡住都调用大模型

**时间回补：v1 2026-10-29 10:25 UTC。** [原论文](https://arxiv.org/abs/2610.39775)。

### 为什么重要

移动机器人在狭窄、非凸环境使用局部 MPC 时，可能陷入“前面不可行、又不能绕出去”的冻结状态。选择继续等待、重新全局规划、后退还是求人工帮助，属于一个低频监督问题。把 LLM 接进每次异常处理会带来网络开销、延迟和无法解释的运行成本。

本研究使用 LLM 作为训练期或新异常时的 Supervisor，将多次恢复经验蒸馏成**可执行的决策树**。通过反事实回放分别标注一次恢复是否必要、无用或有害；后续将无效规则淘汰。

### 算法模块

~~~text
局部 MPC 正常导航
      ↓
检测停滞/局部规划失败
      ↓
现有决策树匹配恢复条件？
  ├─ 是：重规划 / 等待 / 请求帮助
  └─ 否：查询 LLM Supervisor
                  ↓
           反事实执行与对照
                  ↓
          必要/无益/有害 标签
                  ↓
            更新决策树
~~~

### 实验与可靠性边界

在 **20 个未见过的冻结布局**上，蒸馏的树在各随机种子下至少正确处理 **18 个**：要么到达目标，要么在确实没有可行路径时求助。与始终查询 LLM 的 Supervisor 和人工规则相比，性能接近，但**测试阶段不调用 LLM**。

这是仿真监督策略，不是对真实底盘的“无死锁数学保证”。反事实回放的质量取决于仿真器是否能正确预测后退、旋转、碰撞和动态障碍。来自真实部署的新异常必须能够触发安全回退，不应由模型自动赋予危险动作执行权限。

### 可复现性、适合谁与工程落地启发

目前未核实可直接运行的官方代码。在 Nav2 + MPPI 上可先实现简单冻结检测（目标距离长期无进展、速度命令反复振荡），定义三项低风险恢复：原地等待、触发全局重规划、受限后退；对 20 个仿真死胡同做固定种子回放。

适合 **长走廊巡检、机器人自主绕障、ROS2 状态机以及本地/云端 Agent 协作**。最值得研究的是让昂贵模型离开高频控制闭环，并通过独立结果对照剔除“看似聪明但更糟”的恢复动作。

## 4. 行人追踪误差到底来自距离规则还是漏检？把危险漏报拆成可归因问题

**时间回补：v1 2026-10-29 14:52 UTC。** [Decision-Level Error Attribution and Depth-Aware Safety Evaluation](https://arxiv.org/abs/2610.40199)。

### 为什么重要

安全系统往往用二维相机对行人的检测框与估计位置决定“停/走”。某个距离阈值策略即使非常保守，也可能造成过多不必要停车；反过来，深度网络 RMSE 改善也未必真正减少危险漏报。

这篇工作用两因素 Shapley 归因，分离**决策规则的错误**和**感知错误**，再将感知错误细分为“根本没检出”和“检出但定位偏差”。作者还比较仅依据横向距离的停车规则与平面距离规则，并验证横向距离在准确几何前提下是平面距离的下界：因此更容易无谓停车，而不是漏掉同一平面规则能发现的危险。

### 实验数字

基于 ETH/UCY 行人视频，含 **898 名行人、三个场景**。在人工真值位置上，横向距离规则没有漏掉平面规则识别的危险，但停车精确率仅 **5.6%–31.9%**。两组带 RGB 检测的场景中，地面投影定位 RMSE **0.59 m / 0.51 m**，对照几何方法 **1.72 m / 1.39 m**；然而行人检测召回率只有 **0.43 / 0.26**，漏检成为漏报危险的主因。

两倍标准差安全边界在八种场景—阈值组合中匹配或改善漏报率，并在七种组合减少不必要停车。

### 传感器、鲁棒性与实际限制

作者只做**离线停/行决策分类**：使用的是视频和模拟的静止机器人，并没有真实机器人避碰试验。不能把“危险漏报率降低”当作“实地零碰撞保证”。

实际机器人还需要相机标定、地面几何、移动目标速度估计、制动距离和故障时保守减速。尤其不能将检测置信度当作漏检已知度。

### 可复现性、适合谁与工程落地启发

没有确认完整官方复现包。可以用公开行人数据计算四个指标：检测召回、几何 RMSE、危险漏报、无谓停车，再在同一风险预算下替换停车决策规则。采用不同人物划分校准与测试集，不能按视频帧随机拆分导致泄漏。

适合 **人群中机器人、视觉安全 Sidecar、低成本 RGB 行人感知**。工程优先级是先修复漏检，再优化米级定位误差；只有真实闭环评估才能判定最终避碰效果。

## 5. Echo：视觉强化学习不必为每条训练轨迹都支付渲染与视觉编码成本

**时间回补：v1 2026-10-27 19:11 UTC。** [Echo 论文](https://arxiv.org/abs/2610.37865)。

### 为什么重要

端到端视觉强化学习常见的瓶颈是：每个并行仿真环境都要渲染 RGB、运行视觉 Backbone 才能收集经验。经典两阶段路线先训练“特权状态 Teacher”，再蒸馏视觉 Student，但二者目标可能产生模仿间隙。

Echo 颠倒 Teacher/Student 的方向：**视觉策略才是需要优化的主策略**；辅助状态策略模仿当前视觉策略，并在不渲染图像的仿真分支里便宜地收集经验。这些经验通过共享的特权 Critic 做 Off-policy 价值学习，反过来提高视觉策略。

### 算法模块

~~~text
视觉策略 + RGB 观测 ──→ 少量较贵的视觉试验
        │                         ↓
        └→ 状态辅助策略模仿 ──→ 大量无图像仿真
                                  ↓
                          Off-policy Replay
                                  ↓
                             共享 Critic
                                  ↓
                           更新视觉策略
~~~

### 实验结果和边界

作者在 Genesis 中测试三个视觉移动控制任务与两个灵巧手任务。相对所选 SDPG 实验配置，达到参考回报所需时间平均缩短：**移动任务 60%**、**灵巧手任务 56%**；峰值平均回报对应增加 **62% 与 12%**。在相同仿真转换预算下，两项手任务亦有更高平均回报。

论文明确属于**初步研究报告**，不包含普适的真机零样本成功率。状态辅助策略如果过度偏离视觉主策略，离策略数据可能反而伤害训练；Critic 利用特权状态也不能被误解为部署时仍然能读取这些状态。

### 可复现性、适合谁与工程落地启发

尚未确认成熟官方仓库。使用同一 Genesis 场景，比较纯视觉 On-policy、传统状态 Teacher 蒸馏、Echo 风格逆向蒸馏；固定 GPU、环境步数、渲染调用次数及真实墙钟时间。记录视觉策略独立评测回报与 Critic 偏差。

适合 **视觉 RL、机器人端到端控制、仿真吞吐优化和减少训练 GPU-hours**。特别需要同时报告“每秒仿真样本”与“真实机载推理延迟”，绝不能混为一谈。

## 6. DexSuite：30 个灵巧操作任务与 4,700 条成功示范，检验跨机械臂/手泛化

**时间回补：v1 2026-10-27 18:21 UTC。** [DexSuite 论文](https://arxiv.org/abs/2610.37799) · [官方项目/数据](https://dexsuiteorg.github.io/)。

### 为什么重要

机械臂仿真 Benchmark 经常只支持少数固定的末端执行器，平行夹爪和灵巧手的环境定义、任务终止规则、数据结构又互不兼容。DexSuite 基于 Genesis 统一任务 API、遥操作和模拟触觉，提供 **10 种机械臂、12 种末端执行器、30 个任务**。组合后可构成超过 100 种单臂配置及大量双臂组合。

### 算法与数据结构

~~~text
一份任务定义/成功条件
        ↓
可互换机械臂 + 末端执行器
        ↓
Genesis 物理与模拟触觉
        ↓
人工遥操作 / 脚本专家 / 策略采样
        ↓
LeRobot 格式轨迹与统一评测 API
        ↓
训练与不同本体之间的横向比较
~~~

16 个 Benchmark 任务—本体配对释放了总计 **4,700 条成功轨迹**：人工遥操作 700、脚本专家 1,200、机器生成 2,800；官方页面说明每条在 **20 Hz** 下记录前视、腕部图像、本体状态与物体状态，并提供 LeRobot 与 HDF5 转换。

### 数据结果与值得警惕的失败

官网列出的同一任务最好基线表现中，平行夹爪的 Reach 为 100%，Allegro 为 97%；Pick & Place 则分别为 66% 和 76%。更困难任务并没有被解决，例如 Toast Bread 的多项基线几乎全部为零。这表明“基准规模大”和“真实策略能力强”是完全不同的结论。

论文称框架开源，但**截至本次检索项目页仍显示 Code coming soon**；数据可浏览并不意味着完整训练与环境源码已经可构建。没有完整代码时，应该如实标记为“数据先行、框架复现待验证”。

### 传感器假设、适合谁与工程落地启发

模拟触觉取决于 Genesis 接触参数，不保证与真实压阻、光学触觉和灵巧手关节摩擦一致。人机遥操作映射也可能引入不同本体间无法直接比较的偏差。

适合 **LEAP Hand、Allegro、Franka、ALOHA、跨本体训练与数据整理**。建议先下载少量 LeRobot 轨迹，检查动作维度、相机标定、时钟及成功条件，再在统一评测集上比较 BC、Diffusion Policy 与 ACT；真机部署需要独立限位与接触安全。

## 7. Gym-Anything：让 Coding Agent 生成机器人模拟器，并用对抗审计过滤不可靠任务

**时间回补：v1 2026-10-29 17:42 UTC。** [Gym-Anything 论文](https://arxiv.org/abs/2610.40565) · [作者项目入口](https://gym-anything.github.io/)。

### 为什么重要

具身 AI 的世界模型和训练数据长期受限于模拟器场景构建成本：复杂物理任务往往需要专家维护约束、奖励和状态机。Gym-Anything 将创建仿真场景视为 Coding Agent 能完成的程序工程：Agent 编写环境，再由对抗性 Creation–Audit Loop 检查场景是否有意义、成功条件是否能真正检验物理技能。

### 算法模块

~~~text
真实经济活动的任务/物理现象清单
                ↓
        Coding Agent 生成模拟器
                ↓
        对抗审计：任务与环境
                ↓
       修复无效物理/奖励/终止逻辑
                ↓
         RoboWorld Benchmark
                ↓
      策略训练与独立成功检验
~~~

RoboWorld 包含 **25 个仿真、25 个测试环境、175 个训练环境**。作者报告，在指定测试任务中，最强前沿模型全部失败，平均 Reward 仅 **0.06**。论文进一步尝试重复试验的 In-context Learning、读取特权状态的 Teacher、从模型自身经验学习，以及由代码策略生成 VLA 训练示范；这些路径都获得改善，但不能在没有统一基线的情况下拼接为单一提升比例。

### 工程真实价值与风险

这不是“Agent 写出一个 Python Gym 类就拥有可信物理仿真”。更难的是刚体/柔性接触参数是否合理、奖励是否可被作弊、Reset 和成功判定是否泄漏答案、是否真正存在可执行的专家轨迹。

作者提供项目入口并称开放流水线、环境及评测，但本次直接访问项目网页未成功，**完整源码状态没有独立核实**。不能编造 GitHub 地址或依赖安装命令。

### 适合谁关注与工程落地启发

适合 **Sim2Real、机器人任务自动生成、具身 Coding Agent 与 RL Benchmark**。最小尝试是让 Agent 为一个熟悉的 MuJoCo 夹爪场景自动生成两个任务，再人工引入错误摩擦、可穿透物体或无效终止条件，检查审计器是否会拒绝。记录生成环境成功率、可复现种子、Reward Hacking、独立物理检查和总体人力成本。

**把 Agent 自动生成的仿真当作候选实验，而不是自动等同于物理真值。**

## 8. LLM 可复用控制器＋概率模型检验：生成一次规则，逐环境重新验证

**时间回补：v1 2026-10-27 22:50 UTC。** [Reusable LLM-Based Plans with Probabilistic Guarantees for Self-Adaptive Systems](https://arxiv.org/abs/2610.38039)。

### 为什么重要

一个 Coding Agent 生成的控制规则，在当前仿真地图上能够执行，不代表另一张地图、另一种网络丢包率或机器人数量变化后仍满足成功概率要求。传统方法对每一种环境实例重新合成控制器，计算开销较高；无验证地直接复用模型输出又不安全。

本研究采用 Verifier-guided Controller Reuse：让 LLM 产生较通用的规则列表，在具体环境中用概率模型检查器重新判断是否满足该实例的概率性质。检查失败后才能更新或重新生成，**可复用的是候选规则，不是未经验证的保证**。

### 算法模块

~~~text
当前环境概率模型 + 性能/安全要求
                        ↓
            现有规则列表可复用？
                  ↓
            概率模型检查器
              ├─ 通过：在此实例复用
              └─ 失败：反馈给 LLM 修改/重生
                        ↓
                 再次独立检验
~~~

### 实验结果与理论边界

作者用三种 LLM 和三个 Benchmark 测试。在 Gridworld 留出环境中，LLM 规则约 **90%** 通过验证，所比较基线最多 **77%**；重新验证既有规则列表相较为每个实例重新综合，快 **15–103 倍**。这一速度是“验证 vs 重新合成”的比较，不是完整机器人物理控制加速。

检查的保证始终相对于**抽象概率模型与指定性质**。若模型遗漏执行器故障、观测噪声相关性或环境结构变化，形式化检验也不能自动覆盖现实世界。

### 可复现性、适合谁与工程落地启发

当前未确认可用的官方端到端代码库。可以建立有障碍和随机传感失效的 Gridworld，定义到达目标概率下界、危险区域概率上界，由 LLM 生成简单规则表，再用独立概率检验器在多张地图上逐一验证。

适合 **机器人高层状态机、Agent 工具权限、网络退化后的模式切换以及有可证明规则的调度**。不要让语言模型控制器在未通过当前实例验证前获得执行权。

### 技巧 1｜Claude Code 2.1.316：单独设置子 Agent 思考档位，并回归受限文件上传

- **来源**：Anthropic，2026-10-31，[Claude Code v2.1.316 Release](https://github.com/anthropics/claude-code/releases/tag/v2.1.316)。
- **一句话结论**：新增 **CLAUDE_CODE_SUBAGENT_EFFORT**，用于覆盖未单独指定档位的子 Agent 默认推理强度；同一版本也修复受限会话将工作目录外文件上传的权限缺口。
- **具体怎么做**：① 先用 claude --version 核对版本。② 在**测试终端**针对模型支持的档位设置环境变量，启动只读分析任务并观察子 Agent 模型/努力档位是否按预期应用；例如 Linux shell 可临时执行如下示例。③ 单独配置临时工作目录及受限模式，用无害工作目录外文件验证读取与上传的边界，再检查日志是否泄露内容。

  ~~~bash
  claude --version
  CLAUDE_CODE_SUBAGENT_EFFORT=low claude
  ~~~

- **适合什么场景**：Claude Code 多子 Agent、成本控制、长上下文只读代码搜索。
- **注意**：变量仅为**未另行指定**的子 Agent 设定默认值，是否支持具体档位仍取决于模型/版本；推理档位不代表工具权限。安全测试仅使用虚构文件，不接触真实密钥。

### 技巧 2｜Copilot CLI 1.0.106-1：混合换行 C++ 仓库先测 apply_patch 是否产生无关整文件 Diff

- **来源**：GitHub Copilot CLI 团队，2026-10-31，[v1.0.106-1 预发布 Release](https://github.com/github/copilot-cli/releases/tag/v1.0.106-1)。
- **一句话结论**：修复 apply_patch 对混合 LF/CRLF 文件的无关行尾改写，同时修复多行命令粘贴格式丢失和会话异常关闭时用量记录不完整。
- **具体怎么做**：① 在独立测试 Worktree 里准备一个同时包含 LF/CRLF 的无害 C++ 文件。② 通过 Agent 只修改其中一行，不要触碰其余行。③ 使用 git diff --check 和 git diff --numstat 对比修改前后，确认没有整文件换行波及。④ 使用 /clear 后粘贴多行代码块，检查缩进是否保留。

  ~~~bash

  git diff --numstat
  ~~~

- **注意**：此版本标记为**预发布**；在生产使用前应和当前稳定版作 A/B。Git diff 干净不代表功能测试通过，仍需执行最小编译与回归。

## 经典论文回顾

### The Belief Roadmap: Efficient Planning in Belief Space by Factoring the Covariance（IJRR 2009）

**作者**：Samuel Prentice、Nicholas Roy。**2009 年 7 月 21 日在线发表**；International Journal of Robotics Research，第 28 卷第 11–12 期，1448–1465 页。[期刊 DOI](https://doi.org/10.1177/0278364909341659) · [MIT 作者最终稿](https://dspace.mit.edu/entities/publication/31309098-99dd-4c42-972c-2000c5f2eb44)。

### 当年要解决的核心问题

经典 PRM/A* 主要在几何位置空间搜索：路径能否碰障碍、长度是否短。但定位误差会随移动累积；当机器人穿过缺少观测的区域时，即使地图上的路径无碰撞，也可能因位置不确定性太大而无法可靠执行。

真正的规划状态不是单个位姿，而是一个**Belief（概率状态估计）**：既包含估计均值，也包含协方差。直接在 Belief Space 中搜索很昂贵，因为路径每前进一步都要传播状态不确定性。

### 关键数学思想与算法模块

在近似线性高斯运动/观测模型下，位置估计协方差随预测与观测更新变化。BRM 将协方差采用可以高效传播的分解形式，使连续多个预测和测量步骤能够组合为线性传递关系，再把这个计算引入 Roadmap 的候选路径评价。

~~~text
几何 Roadmap 节点 + 不确定性状态
                  ↓
    每条边的运动/观测模型
                  ↓
      因式化协方差传播
                  ↓
    路径末端 Belief 预测
                  ↓
  搜索同时考虑长度与定位品质
                  ↓
         适合定位的路线
~~~

它与“沿着障碍物多走一点就更安全”不同：几何距离与定位信息之间可能存在权衡。论文以 **UWB 无线地标定位**进行实验，展示绕经提供位置观测的区域可避免定位丢失。

### 假设、历史价值与后续扩展

其高效推导主要依赖线性高斯与特定的协方差结构；高度非线性运动、严重多峰定位、错误地图关联或 UWB 的 NLOS 系统偏差都不自动受保证。

BRM 的历史价值，是将**状态估计性能**正式列为路径规划中的决策对象，而不是把 SLAM 当成会永远提供精确位姿的黑盒。后续 Belief-Space Planning、POMDP 近似、Active SLAM、Risk-aware MPC 与不确定性可行性搜索均沿着类似方向发展，但采用不同的计算与风险折衷。

### 与今天研究的关系

今天第一条“Localization-constrained A*”可看成把经典思想变成更明确的约束形式：不是先找最短路线再问能否定位，而是在搜索过程中要求协方差不超限。

对已有 FAST-LIO/ESKF、反光板或 UWB 地标的机器人，可以先做一个不侵入高频里程计的规划测试：同一地图中设置两条路线，一条最短但弱特征，一条绕路却有可靠观测；比较预测协方差、实际 ATE、地标可见性和路线代价。一定要使用独立真值校验滤波器“自称的协方差”是否合理。

**经典结论：最短路径只有在位置足够可信时，才有成为可执行路径的意义。**

## 今日结论

本期最适合直接转化为工程实践的是**分层验证**。定位上，把预测协方差与规划边约束联系起来；空间记忆上，让对象交互结果更新动力学后验；导航上，让 LLM 只给低频监督规则提供候选，并用反事实回放淘汰坏规则。真实人员避障则要把漏检、定位误差和决策规则的贡献分开，不能只报告视觉网络的平均 RMSE。

模型训练方面，Echo 用辅助状态策略获得低成本离策略经验；DexSuite 解决跨机器人和灵巧手任务数据结构不统一的问题，但完整源码发布状态仍需核实；Gym-Anything 把仿真创建交给 Coding Agent，同时暴露出物理审计与奖励作弊的新风险。可复用 LLM 控制器的工作则明确：**每个新运行环境仍需独立检验**，模型输出不会因为可复用而自动正确。

今日 AI Coding 两项直接操作分别是 Claude Code 子 Agent 推理档位/受限上传回归，以及 Copilot CLI 混合行尾补丁回归；两者都可以在无害 Worktree 当天完成，不需要制造大型工程流程。

**工程原则：把模型产生的“建议”与实际被执行的“已验证命令”分开。**

## 最值得深入研究或尝试复现的方向

1. **Localization-constrained A***：在已有地图中模拟 GNSS 盲区与已知地标，固定噪声参数比较协方差上界、路线长度与实际误差。
2. **PhysVLMM 物理后验**：给不同门/抽屉采集受限力—位移数据，验证不同方向的后验宽度与弃答率。
3. **MPC 冻结恢复**：在 Nav2/MPPI 20 个固定仿真异常上比较固定恢复规则、每次查询 LLM、决策树蒸馏。
4. **视觉行人安全归因**：在同一视频测试中分别记录漏检、平面定位、错误停车和危险漏报。
5. **Echo 训练吞吐**：保持视觉模型不变，拆分有图渲染步数与无图仿真步数，报告 GPU-hours、总样本数与最终回报。
6. **DexSuite 数据先行**：下载小规模 LeRobot 轨迹，验证 20 Hz 时间戳、动作维度、传感器状态与任务成功标注。
7. **Gym-Anything 物理审计**：让 Coding Agent 在隔离环境生成一个简单抓取场景，故意引入错误 Reset/奖励，检查自动审计。
8. **概率验证控制器**：固定规则列表，改变随机障碍与传感失效率，衡量每实例复检通过率和成本。
9. **AI Coding 权限与补丁**：分别验证 Claude Code 子 Agent 档位/外目录保护和 Copilot CLI 混合换行安全补丁。
