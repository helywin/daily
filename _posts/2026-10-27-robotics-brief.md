## 1. AF-MCL：四个单点测距传感器实现动态室内环境下的低成本定位

**时间回补：2026-10-23 13:54 UTC，v1。**

### 为什么重要

低成本室内无人机不一定有 16 线雷达、深度相机或可用 GNSS。在有一张已知静态平面地图的房间里，四个方向上的单点测距，加上独立获得的航向，就有机会推断二维位置。但行人、移动物体会遮挡真实墙面，使测距不再对应地图中的静态几何。

该工作提出 Augmented Filtered Monte Carlo Localization（AF-MCL）。它的改进不在于让粒子数无限增长，而是先判断哪些量测与已知静态地图一致，再利用有效测距更新位置后验；当估计偏离或者机器人被搬动时，主动注入新粒子恢复。

### 算法模块和传感器假设

    四个单点测距 + 已测 Heading + 先验静态二维地图
                       ↓
               射线与地图一致性分类
                       ↓
          丢弃疑似动态遮挡的测距
                       ↓
             粒子传播 / 观测更新
                       ↓
              自适应注入恢复粒子
                       ↓
                (x, y) 与置信度

射线分类只在**上一时刻的位置估计**处进行，使这一步 Ray-casting 的成本不随粒子数量同比增长。这是有价值的工程简化，但上一时刻估计严重错误时也可能误判传感器读数。

系统要求已知静态平面地图、量程标定及可靠航向。输出属于二维位置定位，**不是未知环境三维 SLAM**，也不能仅靠四个距离恢复完整六自由度姿态。

### 实验、实时性与鲁棒性

作者在 **2.10 × 1.63 m** 的真实小型空间内报告静态/动态条件平均位置误差 **6.4–7.7 cm**；在 6×6 m 和 10×10 m 的仿真中为 **4.5–5.2 cm**。动态障碍条件下，普通 MCL 为 **12.3 cm**，另一可靠 MCL 对照为 **7.7 cm**。真实台架面积较小，不能由此推断在整层建筑仍保持厘米级精度。

摘要未给出跨平台 P99 计算时间或成熟官方代码。狭窄走廊对称结构、多次连续动态遮挡、地图变化、测距失效，仍可能使粒子分布多峰。

### 适合谁关注与工程落地启发

适合低成本无人机、室内小车、几何环境简单但有动态遮挡的实验台架。建议先用相同的地图和录制数据比较普通 MCL、量测筛选 MCL、AF-MCL；记录有效量测比、Effective Sample Size、重定位成功率和实际 CPU 耗时。对于已有 FAST-LIO 的平台，可把它用作**受限制空间的独立低成本定位备份**，不能直接替代三维 LIO。

来源：[AF-MCL 论文](https://arxiv.org/abs/2610.32645)。

## 2. Natural-Language to Nav2：把临时通行规则变为确定性可审查的 Costmap 策略

**时间回补：2026-10-23 13:44 UTC，v1。**

### 为什么重要

真实工厂或仓库会出现临时禁区、仅允许某些人员接近的区域、不同班次的通道策略。LiDAR 能发现实际障碍，却无法从障碍本身知道“今天这个门不允许通过”。

这项研究不让 LLM 每帧生成 Twist，也不替换 Nav2。它让**本地小模型只负责把操作员语言整理为受约束的 JSON 政策**，再由确定性检查器决定是否接受，最后投影到既有 Costmap 层。

### 算法模块

    自然语言（目的地 / 禁区 / 区域偏好 / 时间事件）
                         ↓
                     本地 LLM
                         ↓
                  JSON Policy
                         ↓
                 Schema / 语义校验
                         ↓
              三种 Costmap Adapter
                         ↓
                  原有 Nav2 栈
             Planner → Controller → Robot

约束包含目的地、空间区域、时间或者事件条件。真正运行时需要保证地图坐标、区域多边形、策略来源与过期时间一致。自然语言生成的命令在 Schema 上合法，并不保证业务语义正确。

### 实验与风险边界

**150 条**研究人员撰写的英文命令中，四种本地模型分别生成 **107–142 条正确且接受的策略**，规则解析器为 44 条；不同模型同时存在 **3–20 条错误接受**。作者进行 8 项端点/JSON 故障及 29 项验证阶段故障的拒绝测试。在 TurtleBot3 真实测试的指定任务中，相对不含这些策略的基线，平均行驶时间降低 **23.1%–35.0%**；在仿真中降低 **18.4%–24.5%**。这是特定任务和对照的行驶时间变化，**不是通用导航算法提速**。

最重要的风险是“错误接受”。禁区策略若被错误理解，可能产生越权通行。建议对重要禁区使用明确的管理员来源和独立批准，而不是只相信 LLM 解析结果。

### 适合谁关注与工程落地启发

适合 ROS2/Nav2、工厂巡检、语义导航和按班次调整路线的机器人。建议使用静态 JSON 策略先跑通 Keepout、Zone Cost 和时间门禁，再接 LLM；用恶意多边形、无效坐标系、过期事件时间做负向测试。**本地 LLM 是策略录入助手，安全与权限交给独立 Validator 和底层 Costmap。**

来源：[论文](https://arxiv.org/abs/2610.32633) · [作者项目页](https://a56239637-dot.github.io/Natural-Language-to-Nav2-Project-Page/)。

## 3. RepresentNav：在导航目标驱动的自建潜空间中提前“想象”下一帧

**时间回补：2026-10-22 UTC，v1。**

### 为什么重要

使用视觉基础模型做导航，通常直接拼接预训练 Encoder 的特征。但分类、分割和深度模型预训练目标不同；把它们的最终特征直接拼起来，未必保留沿路径绕障最需要的信息。

RepresentNav 不简单选择某个大模型的最后一层，而是从多个视觉基础模型的不同深度提取信息，再通过紧凑的三层 Transformer 形成**导航任务自己塑造的视觉表征**。

### 算法模块和观测假设

    摄像头当前帧 → 多模型、多层视觉特征
                           ↓
                   Representation Residuals
                      （三层 Transformer）
                           ↓
                    导航专属潜空间
                      ↙          ↘
                Action Head     JEPA 预测下一潜状态
                      ↖          ↙
                     联合训练与执行

JEPA 在动作前预测短时未来表示。论文报告潜状态还可解码深度、语义以及三维占据信息，但占据本身并未被直接监督。因此，这种潜空间的“像地图”性质，不能直接等同于经过测量校准的 SLAM 地图。

### 实验、实时性和鲁棒性

作者报告 VLNVerse 细粒度任务成功率 **83.80%**，比此前最佳高 **20.05 个百分点**；EVT-Bench distracted tracking 单摄达到 **85.5%（+10.1）**。其预测潜状态减少了相关实验约四分之一的碰撞，且有真实机器人穿行动态人群的展示。

这些来自多套不同基准，不能相互相加。论文未公布对任意 Jetson/RK3588 的统一端到端推理延迟；多编码器可能增加前端算力与内存。

### 适合谁关注与工程落地启发

适合视觉目标导航、VLN、端侧多视觉 Encoder 和场景预判。建议固定 Encoder，分别比较“最后层拼接”“多层 Residual”“再加入 JEPA”的实验，并测量 P95 摄像头到控制命令时延、碰撞净空和任务成功率。对实际巡检机器人应继续使用几何 Costmap 负责硬障碍约束，不能让隐式世界预测直接授予碰撞安全保证。

来源：[RepresentNav 论文](https://arxiv.org/abs/2610.31762) · [项目页](https://wang-yinxi.github.io/representnav/)。

## 4. BM2PC：柔性绳索操纵同时保留多个控制模式，并补偿末端实际执行失配

**时间回补：2026-10-22 19:35 UTC，v1。**

### 为什么重要

对绳、线缆和软管执行高速操作时，一个目标路径可能有多种合法绕障模式。只保持一条最优候选，容易陷入某个不利的局部解；而采样式 MPC 产生过多候选，又可能超过实时预算。

BM2PC 将 Multimodal MPC 形式化为贝叶斯的**控制序列集合优化**：不仅选择分数高的控制，还要保留行为不同的多条潜在解，并用低成本增量贪心更新。

### 控制模块与真实执行模型

    多种候选控制序列 / 柔性物状态
                      ↓
              Bayesian Set Optimization
                      ↓
             高质量 + 多样性候选集
                      ↓
           Execution Dynamics（GRU）
                      ↓
         预计真实末端运动 / 柔性物 Rollout
                      ↓
            选择与执行当前前缀
                      ↓
                 下一周期重规划

作者特别强调命令与真实末端执行不一致，使用 GRU 模型预测实际运动。它依赖机器人实际末端轨迹、执行延迟和所操纵材料的范围；软管材料与训练数据差异过大，仍需要保守验证。

### 作者报告的结果

官方源码说明，增量模式集合更新约 **1.55 ms/步**，相对于穷举集合优化平均最优性差距 **1.14%**；其执行模型平均最大误差约 **0.43 cm**，对比原始命令—执行失配 **4.57 cm**。最长真机跟踪任务的 RMSE 下降 **44.0%**；避障规划时间相对相应多模态 MPC 对照下降 **29%–66%**。

这里 1.55 ms 是特定模式集合更新的耗时，不是完整相机—感知—求解—电机响应的总时延。硬件实验在 Franka Panda 上完成，不可直接外推到其他动力学。

### 可复现性、适合谁关注与工程落地启发

官方已公开 MuJoCo、NVIDIA Warp 绳索仿真、控制器和 Franka 相关代码。可从官方仓库运行相同轨迹对照，固定 Rollout 数与障碍几何，分别关闭“多模式保留”和“执行响应模型”，记录真实跟踪 RMSE、最小障碍净空及完整 MPC P99。对已有速度接口的机器人，更值得直接借鉴的是“**命令不是实际执行**”的建模思想。

来源：[论文](https://arxiv.org/abs/2610.31852) · [官方源码](https://github.com/Longyouyuan/BM2PC)。

## 5. 人形控制器的延迟裕量：40 ms 命令延迟就能使看似稳定的策略失效

**时间回补：2026-10-23 07:35 UTC，v1。**

### 为什么重要

人形 Locomotion 策略经常在训练模拟器达到很高成功率，再迁移到 MuJoCo 验证。若两端控制周期、动作零阶保持或网络延迟没有正确对齐，所谓的 Sim2Sim 差距可能来自 Harness，而不是物理模型差异。

该研究用 **24 关节人形、五种视频动作、三个随机种子**，专门测量命令延迟扰动。结论并非“所有时延都应该随机化”，而是**训练随机化范围应覆盖真实平台测得的关键时延**。

### 实验设计与指标

    同一动作/模型/训练预算
              ↓
    Train A：不做额外命令延迟随机化
    Train B：0–50 ms 延迟随机化
              ↓
       独立 MuJoCo Harness
              ↓
     固定 0/20/40/... ms 执行延迟
              ↓
      动作生存率 / 跟踪误差 / 裕量

在 40 ms 固定命令延迟下，不随机化模型的平均生存率仅 **15%**，测得延迟裕量约 **20–30 ms**；训练时随机 0–50 ms 后，同一延迟下平均生存率提高到 **95%**，裕量扩大到 **50–70 ms**。相同额外训练迭代、但不施加延迟随机化的对照没有带来该收益。

代价是部分动作跟踪精度略变差（四种动作约 0.02–0.06 rad），且最激烈动作对其他扰动的鲁棒性可能减弱。论文还发现最初 Sim2Sim 差异来自**测试 Harness 漏了地板以及时间步配置错误**。

### 适合谁关注与工程落地启发

适合 Unitree G1、双足动作跟踪、ROS2 控制与遥操作。首先测量真实“输入发布→机器人执行器反馈”的 P50/P95/P99，再设计随机时延范围；对照不同命令保持方式和丢包模式。不要用多写几份测试报告来替代实际时钟与物理更新率的核实。

论文结果主要来自仿真交叉验证，不应包装成已通过真机功能安全认证。

来源：[论文](https://arxiv.org/abs/2610.32277)。

## 6. FORCA：Coding Agent 读取力/力矩曲线，再修改接触控制程序

**时间回补：2026-10-22 19:24 UTC，v1。**

### 为什么重要

让 Coding Agent 写机器人操作 Python 程序时，如果它只得到图像或最终“成功/失败”结果，往往无法区分末端位置偏差、接触力不足、突然卡住还是表面摩擦变化。

FORCA（Force-Aware Coding Agent）让 Agent 同时读入视觉观察和腕部六维力/力矩记录，生成带接触探测和力反馈分支的 Python 控制程序。执行之后，Agent 可以根据实际力曲线重新判断失败原因，并更新运动或接触逻辑，而不是盲目重复同一段动作。

### 算法模块与接口

    任务指令 + 摄像头 + Wrist F/T
                 ↓
          Coding Agent
                 ↓
       有界 Python 操作程序
        ├─ 探测接触
        ├─ 受限运动
        └─ 力反馈逻辑
                 ↓
           Robot Execution
                 ↓
       F/T Log + Visual Outcome
                 ↓
      诊断失败并修改下一版本

作者报告不需要任务专用示范、微调或模拟器，覆盖 **五项真实机器人任务**，展示抓取精度、表面性质适应，以及擦拭、剥离中的接触维持，相比视觉版本有改善；摘要未提供通用成功率数值，不能推断五项任务已经达到工业级可靠率。

### 工程安全、可复现性和适合谁

这是一类“**AI 生成真实运动代码**”的高风险接口。建议从仿真或受控台架开始，仅开放有限的 read_state、probe_contact、safe_move、stop；限制每次动作的速度、位移、接触力和最大持续时间，禁止 Agent 修改安全阈值或任意直接执行系统命令。

评估时将定位偏差、接触丢失、法向力峰值、横向力峰值和实际成功率分开统计；每次程序版本都关联执行日志，但不需要生成大量冗余审计文档。未经独立检查的生成程序不应直接执行在有人协作的工业机械臂上。

来源：[FORCA 论文](https://arxiv.org/abs/2610.31841) · [作者项目](https://tanoom.github.io/forca/)。

## 7. VLA 全权重微调陷阱：没有 FP32 Master Weight 时 BF16 会吞掉真实梯度更新

**时间回补：2026-10-22 19:45 UTC，v1。**

### 为什么重要

BF16 推理和混合精度训练通常节省显存，但**用 BF16 存储需要直接被更新的主参数**与“计算时使用 BF16”不是一回事。AdamW 的小幅更新写回 BF16 参数时，可能因为有效尾数不够而被舍入为零，训练日志显示有 loss、梯度和 optimizer.step，却没有真正更新足够多的参数。

该研究检查了 **12 个开放 VLA 代码库**，其中 9 个存在默认或文档化的相关训练配置。作者在 LIBERO 实验中发现，特定配置下对 BF16 权重的更新至少 **79% 被舍入抹去**。

### 结果与工程含义

在 LIBERO-Object 上，保留 FP32 主参数使 SmolVLA 特定低学习率设置成功率由 **4.3%→49.3%**，π0.5 由 **5.1%→80.9%**；在 π0.5 默认学习率实验由 **89.0%→97.7%**。这几组设置、学习率及动作 Chunk 条件不同，不能相互相加，也不能推断所有 LoRA 或量化训练都存在同等问题。

### 可复现方式

首先只读检查训练代码：进入 AdamW 的 trainable Parameter 是否为 BF16；是否存在 FP32 Master Copy；实际优化器状态以及参数更新大小是否正确。最小测试建议从模型参数的小样本开始，固定数据、种子、学习率和 Batch，记录：

    trainable_dtype
    master_weight_dtype
    fraction_of_zero_effective_updates
    loss_curve
    heldout_task_success

**保留 FP32 可训练主权重，让前向计算使用 BF16 autocast**，是和“所有可训练权重都 BF16”不同的配置。切换后显存占用可能增加，需先验证所用训练框架的实际更新路径。

### 适合谁关注与工程落地启发

适合 LeRobot、SmolVLA、π0/π0.5、Flow Action Expert 与自训练端侧 VLA。最优先的排查顺序是先确认参数是否真的更新，再追求更长训练、更多数据和更大的模型。它不是无需验证即可套用的通用加速技巧，而是可被数值实验检验的训练正确性问题。

来源：[原论文](https://arxiv.org/abs/2610.31859)。

## 8. Pairing Matters：同一轻量 Coding Model，换 Harness 的成功率可能差 44 个百分点

**时间回补：2026-10-23 UTC，v1。**

### 为什么重要

本地运行小模型做 Coding Agent 时，最常讨论的是模型参数量、推理速度、榜单排名。但 Agent 的搜索、编辑、测试反馈、错误恢复和上下文管理全部由 Harness 决定。

一款模型在某个 CLI 中表现不错，迁移到另一个工具就可能明显退化。研究者对 **6 个开源 Harness × 3 个轻量模型 × 100 个 SWE-bench Verified Issue**执行 **1,800 次**可评分的全因子实验，并分析 **1,100 次失败运行**。

### 核心结果

在相同模型下，不同 Harness 的任务解决率最多相差 **44 个百分点**；Harness 的排名也随模型改变。即使限定同为模型驱动循环的 Harness，每个成功任务所收取的 Token 数还可能相差 **20 倍以上**。

这不是说明某个 Harness 永远最好，而是说明“模型—Harness 配对”才是实际部署单位。模型分数高、Token 消耗低，也不代表代码一定符合当前仓库的测试与权限契约。

### 可执行的对照设计

    同一 Git Commit / Issue / 可见上下文 / 预算
                          ↓
              Model A × Harness 1/2/3
                          ↓
              独立隐藏验收测试
                          ↓
    resolved_rate、tokens_per_success、wall_time
             tool_failures、unsafe_edits

建议用 10–20 个项目真实修复任务，固定模型供应端与预算，比较最小文件读取循环和复杂多 Agent Harness。将错误定位、补丁应用失败、测试误读和过度工程化分类，不要把失败全部归因于模型推理能力。

### 适合谁关注与工程落地启发

适合 DeepSeek/Qwen 本地 Coding Agent、Codex 类 Harness、OpenCode、自研 CLI，尤其适合想减少无用文档和防御性编程的研发团队。**先做同模型 A/B，不要在缺少证据时将整个工作流一次性复杂化。**

研究公开了实验记录与分析材料，但完整重放还需要检查模型版本、托管配置及 Harness Commit。论文结果不能当成全部企业仓库的统一效果。

来源：[论文](https://arxiv.org/abs/2610.32131)。

## AI Coding 实战技巧精选

### 技巧 1｜检查 Claude Code Edit 工具的符号链接 TOCTOU 漏洞是否已修复

**来源：** Anthropic / GitHub Security Advisory，**2026-10-26**，[GHSA-5xjx-9qx6-jcrv](https://github.com/anthropics/claude-code/security/advisories/GHSA-5xjx-9qx6-jcrv)。

**一句话结论：** macOS 上，旧版 Claude Code 在 Edit 写文件前只做路径瞬时验证，恶意仓库脚本可能通过交换目录与符号链接，使写操作落到 Workspace 之外。**受影响版本低于 2.1.251；2.1.251 已修复**。

**具体怎么做：**
1. 运行下面的只读版本核对，找出未更新的开发机或 CI Runner。
    
        claude --version

2. 对手工安装环境按照 [官方安装/更新说明](https://code.claude.com/docs/en/setup) 更新到不低于修复版本；自动更新用户仍应核查版本。
3. 对不可信仓库，在升级前禁止执行未审查的安装脚本，并在容器/独立工作树中限制文件可写范围；仅在无害测试目录验证沙盒与实际文件权限。

**适合什么场景：** macOS Claude Code、本地多仓库开发、下载第三方项目后运行 Agent。

**注意：** 该公告描述的是特定工具写入竞态及前提条件，不是所有 Claude Code 版本均可无条件访问任意文件；升级也不能替代最小操作系统权限。

### 技巧 2｜使用 gh-aw v0.93.5 审查 Agent Workflow 的凭据跨步骤传递

**来源：** GitHub Agentic Workflows 官方 Release，**2026-10-25**，[v0.93.5](https://github.com/github/gh-aw/releases/tag/v0.93.5)。

**一句话结论：** 本次官方发布增强了 Secret-leak 分析对**步骤输出中的凭据传递**的跟踪，并改善了 Engine Crash 的去敏诊断。适合在已有 Agentic Workflow 中执行编译检查与历史运行审计。

**具体怎么做：**
1. 在安装了 gh-aw 的测试仓库核对版本并编译已有 Markdown Workflow。

        gh aw version
        gh aw compile

2. 对真实存在的测试 Workflow Run 执行只读审计。

        gh aw audit RUN_ID --json

3. 检查凭据是否经 step outputs 流入不应获得它的步骤；使用临时假凭据跑负面测试，并对比升级前后的编译告警和权限边界。
4. 对需要接触真实凭据的 safe-output 集成步骤，仅授权对应 job 所需范围，避免把整个 Repo Secret 集合传递给 Agent。

**适合什么场景：** GitHub Actions、gh-aw、定时 Coding Agent、带发布/Issue 写入权限的工作流。

**注意：** 新版本允许某些 safe-output 集成 job 使用网络凭据，不意味着所有网络出口均安全；禁止在公开构建日志输出完整 Secret。审计报告也不能替代运行时权限限制。

## 经典论文回顾

### The Vector Field Histogram—Fast Obstacle Avoidance for Mobile Robots（Borenstein & Koren，1991）

**发表时间与历史位置：** Johann Borenstein 和 Yoram Koren 的论文发表于 **IEEE Transactions on Robotics and Automation，7(3):278–288，1991 年 6 月**；DOI：[10.1109/70.88137](https://doi.org/10.1109/70.88137)。这是早期高速局部避障从原始传感器量测抽取方向决策的代表性工作。

#### 核心问题与数学思想

机器人面对密集障碍时，纯粹由当前最近障碍产生排斥方向，容易在狭窄环境振荡。VFH 将距离传感器更新的二维 Histogram Grid，投影为机器人周围的**一维极坐标障碍密度直方图**，再从障碍密度低的扇区选取朝向目标的局部转向方向。

    Sonar / Range Readings
            ↓
      Cartesian Histogram Grid
            ↓
      Polar Obstacle Density
            ↓
      Candidate Open Valleys
            ↓
      Heading / Steering Choice
            ↓
         Robot Motion

直方图的数值实际上是局部障碍结构的信息压缩，它不是对未来整条轨迹的动力学可行性证明。

#### 传感器、实时性与历史意义

原工作面向车载距离传感器（尤其超声波）和二维地面机器人，依赖传感器覆盖、栅格更新和速度/转向执行能力。在作者测试的拥挤障碍场景中，机器人平均以约 **0.6–0.7 m/s** 连续绕障。它证明了无需大型全局优化器，也可以把高频环境几何实时转换为目标方向引导。

#### 今天仍然保留的思想和已被替代的部分

保留下来的核心是**观测层压缩到控制层可用的局部方向成本**。后续 VFH+、DWA、TEB、MPC、MPPI 与学习式导航使用了更明确的机器人形状、速度约束和预测模型。

原始 VFH 不处理三维地形、复杂动力学、语义通行权限或行人未来行为，也不能独立解决死胡同中的全局路径选择。因此它不应代替现代 Nav2 局部控制器和独立安全过滤。

#### 可复现性与工程重新解读

无需重建当年的硬件：使用 2D LiDAR/Ray Tracing 生成局部 Histogram Grid，构造 1D Polar Histogram，并对比相同场景下的 Nav2 DWB 或 MPPI。记录最小障碍净空、振荡次数、路径长度和 CPU P95。

今天的 AF-MCL 将距离传感器用作**定位观测**；VFH 将距离传感器用作**局部运动选择**。同一种测距技术可服务不同任务，但测量被地图解释的假设与被控制器使用的假设必须明确分离。

原始资料：[IEEE 期刊 DOI](https://doi.org/10.1109/70.88137) · [作者原论文公开版本](https://public.websites.umich.edu/~ykoren/uploads/The_Vector_Field_HistogramuFast_Obstacle_Avoidance.pdf)。

## 今日结论

本期最重要的不是单个模型又刷新了多少 Benchmark，而是**哪些状态真正可信、哪些动作具有有效的执行语义**。

AF-MCL 说明动态障碍导致的距离量测必须先经过地图一致性判断。自然语言 Nav2 将临时规则和机器人本身的物理避障分层。RepresentNav 展示未来视觉潜状态可以为导航带来收益，但不能自动替代几何安全地图。BM2PC 让多种候选控制保持活跃，同时显式学习实际执行器与命令之间的差距。

人形延迟研究指出，哪怕物理模型一致，如果 Harness 漏了地板或者时钟配置错误，Sim2Sim 评测就可能失真。FORCA 用真实接触力反馈纠正 Agent 生成的控制程序。VLA BF16 工作提醒模型训练本身可能发生静默数值失败。Pairing Matters 则表明 Coding Agent 应比较模型与 Harness 的组合，而不是靠增加层层防御和文档推断效果。

本期两个实战技巧也落在明确边界：**文件写入权限由真实文件系统与修复版本保证，Agent Workflow 凭据跨步骤流动则需要静态分析和真实授权检查。**

工程优先级建议是：先修测量、时钟、优化器数值和任务验收的真实性，再增加世界模型或新 Agent 层数。

## 最值得深入研究或尝试复现的方向

1. **四测距 AF-MCL：** 固定室内平面地图，注入移动障碍和绑架重定位，比较有效量测占比、恢复率与 CPU 预算。
2. **自然语言 Nav2：** 先用手写 JSON 完成 Keepout / Zone Cost / 时间约束，再加本地 LLM，统计错误接受而不只是正确解析。
3. **RepresentNav 表征消融：** 对相同视觉 Encoder，比较多层残差与 JEPA 潜预测，测量端到端延迟、碰撞和目标成功率。
4. **BM2PC：** 复现官方 MuJoCo/Warp 仿真，分别关闭模式多样性和实际执行 GRU；在一致 Rollout 预算下对比。
5. **人形延迟裕量：** 从实际控制器测量 20/40/60 ms 指令到执行延迟，将实测分布注入 Sim2Sim 而非拍脑袋设随机化范围。
6. **FORCA Robot Harness：** 在隔离台架上只开放带限幅的力探测和安全位移接口，禁止 Agent 修改底层保护规则。
7. **VLA BF16 主权重：** 抽样测量 trainable 参数有效更新非零比例，再以 FP32 Master Weight A/B 对比成功率和显存。
8. **轻量 Coding Agent Harness：** 固定小模型及真实仓库 Issue，比较简单循环和多 Agent 工具流的每成功任务 Token、修复率与过度工程化。
9. **AI Coding 工具安全：** 核查 Claude Code 版本；在 gh-aw 测试 Workflow 上检查跨步骤 Secret 和失败审计。
